十几个 Agent 窗口开着，热闹得像个小办公室：这个文件归谁？两队是不是又造了同一个轮子？怎么最后还是你在来回传话？

**请坐老板位：定目标、作取舍、看交付。** CTO 统筹项目，规划拆任务、带队、协调依赖、收集证据。你可以找 CTO，也可以直接找规划，办公室的传达室不用你兼任。

AI-Company 是一套精简、可阅读的协作手册，面向**需要多个 AI 团队共同推进的大型软件项目**。你使用自己的编程助手和任务工具，这个仓库提供角色、通信、交接与交付规则。

## 开工指南

**1. 先给手册安排个工位。** 把本仓库下载或克隆到业务项目旁边，然后在编程助手里打开**你要开发的项目**。

```text
workspace/
  your-project/   <- 你要开发的应用，打开这里
  AI-Company/     <- 给 AI 看的协作手册
```

```sh
git clone https://github.com/Timking123/AI-Company.git
```

助手能浏览仓库文件时，也可以直接给它链接。两个位置分工不同，别一不留神把团队建在手册仓库里。

**2. 填好三个字段，把任务交出去。** 替换所有方括号中的内容。

```text
目标项目：[你要开发的项目路径]
工作流手册：[AI-Company 的路径或链接]
本次目标：[希望交付的一个具体成果]

我担任人类负责人。把 AI-Company 用于“目标项目”。
“工作流手册”只供参考，不是这次要修改的业务项目。
读取手册的 AGENTS.md，并按其中的顺序阅读。

先确认两个位置、可用工具、项目规则和已有工作。
建立唯一 CTO，优先复用现有规划，再创建实际需要的团队。
在宿主允许的范围内创建持久、可见的任务；每个工作 Agent
有唯一管理者和独占写入范围。

规划在职责范围内直接沟通，重要结论同步 CTO。
保留已有授权和项目质量门。先返回能力核验、所有权关系
和下一项可执行工作。缺少必要工具时，说明最小人工操作，
不要宣称团队已经运行。
```

**3. 看第一张点名表。** 应当有真实任务身份、明确负责人、依赖和每个活跃方向的下一步。可以对照[完整填写样例](docs/EXAMPLES.md)：它展示交接应该长什么样，项目、任务标签与结果均为虚构示范。

## 认识你的公司

![一个人类负责人与 CTO 和三个方向规划交互。每个规划只管理自己的工作 Agent，规划之间直接协调，并向 CTO 同步重要结论。](assets/organization.svg)

| 你联系谁 | 它负责什么 |
| --- | --- |
| **CTO** | 项目方向、团队归属、公共设计、冲突、重复工作和集成顺序 |
| **方向规划** | 一个方向的完整闭环：方案、任务分配、审查、修复和交付 |
| **工作 Agent 由所属规划管理** | 范围明确的实现、调查、测试或独立复核 |

规划之间可以直接沟通。在已分配范围内确认事实、约定交接，再把有影响的结论同步给 CTO。公共设计、文件归属、跨方向优先级和验收标准变化由 CTO 裁决。你已经明确决定的事情，不需要再批准一次。

## 同样的工作量，缩短关键路径

![示意排期：一个单位规划、四项各两个单位的独立任务、一个单位集成。串行耗时十个单位，四个工作槽并行耗时四个单位；两种安排都包含十个工作单位。](assets/parallel.svg)

**这是一张排期示意图，不是性能测试。** 两种安排的工作内容完全一致：1 个单位规划 + 4 项独立任务 × 2 个单位 + 1 个单位集成。串行使用一个工作槽，并行使用四个。理想经过时间是 **10 → 4 个单位**，总排定工作量仍是 **10 个单位**。

实际协调、模型延迟、限流、依赖和返工可能降低甚至抵消收益。图中不宣称 Token 节省、API 成本下降或产品实测提速。

> 独立工作并行推进，公共决策与集成统一协调。

## 使用你自己的编程助手

这套工作流采用通用 Markdown。[客户端目录](docs/COMPATIBILITY.md)已覆盖 27 个条目，逐项提供官方来源、读取入口和限制：

| 工具类别 | 已纳入的客户端 |
| --- | --- |
| 终端与桌面 | Codex、Claude Code、pi、Gemini CLI、OpenCode、Factory Droid、Aider、Amp、Qwen Code |
| IDE 与编辑器 | Cursor、Windsurf / Devin Desktop、GitHub Copilot、Cline、Kilo Code、Continue、Augment / Auggie、Kiro、Antigravity、TRAE、Qoder、Junie、Amazon Q Developer、ZCode |
| 托管平台与 SDK | OpenHands、Devin 云端、Replit Agent |
| 历史参考 | Roo Code，明确标注官方停运状态 |

**文档覆盖不等于运行认证。** 部分客户端需要独立规划会话、经过核验的扩展或人工转交。原生子代理也不自动等于持久、可嵌套的公司组织；创建团队前应核对具体客户端、版本和权限。

## 让公司正常运转的几条规则

- **一个工作 Agent，一个管理者。** 接受创建它的规划，或正式登记的继任规划管理。CTO 通过规划调整工作。
- **一个文件，一个写入者。** 独立可写任务使用隔离工作区和明确文件范围。公共契约与集成有指定负责人。
- **先复用，再扩充团队。** 查阅已有任务、代码和决策，再创建新团队或抽象。并发数量要匹配审查与集成能力。
- **同步信息，继续执行。** 规划向 CTO 上报你的要求和决定；已授权工作不因上报增加一次审批。
- **凭证据交付。** 实现、验证、集成、部署分别记录。候选变化后，完成新候选所需的检查。
- **留下有用的经验。** 规划维护范围明确的备忘和可复用方法，由 CTO 判断哪些经验进入项目规则。

小修可以由一个规划直接完成。改个按钮文案，不需要召开公司大会。

## 使用预期

这是一个**试行中的文档工作流**。它没有附带调度引擎、文件锁执行器或 Agent 运行时。宿主需要提供任务、通信、文件系统和版本控制能力；模型仍可能误解规则，采用前应完成接入检查和验收场景。

CTO 和规划使用你选择的强规划模型及其支持的高推理设置。质量优先预设可以选择当前主力模型与最高支持强度。记录实际型号和设置，尊重用户选择，与应用或评测系统的模型配置分开。

## 老板，第一天上班还顺利吗？

先用一个范围明确的方向试试，再[交一份简短的试用反馈](https://github.com/Timking123/AI-Company/issues/new?template=tryout.yml)。用了哪个助手？哪里配合默契？哪里又绕成了毛线团？哪怕只是一句指令让你困惑，也值得告诉我们。

分享脱敏案例，不用交出整个项目。重复任务数、用户介入次数、集成等待时间和验收结果都是有用的证据。反馈表只问关键情况，不要求搬来完整聊天记录。

让新增内容保持精简。优先改清一条规则或补一个例子，再考虑增加管理层。
